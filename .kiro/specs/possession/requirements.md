# Requirements Document

## Introduction

The `possession` spec defines the possession detector of Ghost Run+. A possessed agent is one that was manipulated by hidden instructions in text it read (prompt injection). This spec covers four parts:

1. **Blacklight**: a pure scan that finds hidden text (Unicode tag characters outside the RGI flag sequences, zero-width characters, bidi control characters, and HTML comments in markdown) and reports where each finding is and what it says.
2. **Sanitize**: a pure function that removes the hidden text and keeps everything else.
3. **Red thread**: a record format for the texts an agent read during a session, plus a pure lookup that links an address, host, or file path in a ghost action back to the first line that mentioned it.
4. **Scan entry point**: an interface that the `blacklight-steering` hook (File Save on `.kiro/**`, created later by the `kiro-integration` spec) can call to scan files.

Detection is a pure TypeScript function with no runtime dependency. It runs unchanged in the browser (Playground) and in Node. It is the implementation of safety property P7 ("hidden Unicode is always flagged; ordinary Hangul, emoji, and combining marks are never flagged"). The emoji in that claim include the England, Scotland, and Wales flag emoji, which are built from Tag_Characters; the scanner allows a run of Tag_Characters only when it forms an RGI_Tag_Sequence. The world-contract steering claims P7 everywhere.

Text analysis is one layer only. It does not catch every injection, and this spec does not claim that it does. The action-based criterion (a secret file is read, then an unapproved network attempt follows) belongs to the `wards` spec (property P6) and is not claimed here.

This spec reuses the types of `core/src/types.ts` (`Effect`, `ObservedEvent`, `GhostReport`) and defines no second shape for any of them. It adds new types only for findings, provenance records, and red-thread links.

Safety claims follow the world-contract steering ("Claimed in" column):

| Property | Claimed where | Not claimed |
|---|---|---|
| P7 hidden text is flagged, ordinary text is not | Everywhere (pure function: Playground, Node, Docker box host, hook) | n/a |
| Red-thread lookup is the first occurrence | Everywhere (pure function) | n/a |
| P6 secret egress block (action-based) | Owned by the `wards` spec | Not claimed by this spec |

Hidden characters are never written literally in this document. Every hidden character is named by its code point, for example U+200B.

## Glossary

- **Blacklight_Scanner**: The pure function `scanText` that finds hidden text in a string and returns a `ScanResult`.
- **Sanitizer**: The pure function `sanitizeText` that removes hidden text from a string.
- **Red_Thread_Tracer**: The pure functions `collectNeedles` and `traceRedThread` that link a Needle to a cause line in the Provenance_Log.
- **Scan_Entry_Point**: The Node-usable interface of Requirement 11 that scans text or files and returns a `BlacklightReport` with an outcome.
- **Hidden_Category**: One of four values: `tag`, `zero-width`, `bidi`, `html-comment`.
- **Tag_Character**: A code point in U+E0000 to U+E007F.
- **Zero_Width_Character**: A code point in U+200B to U+200D, U+2060, or U+FEFF.
- **Bidi_Control_Character**: A code point in U+202A to U+202E or U+2066 to U+2069.
- **RGI_Tag_Sequence**: A code point sequence listed under `RGI_Emoji_Tag_Sequence` in the Unicode file `emoji-sequences.txt`, of the Unicode/Emoji version and generated by the method recorded in Design Decision D3. Each such sequence is the base U+1F3F4, then Tag_Characters, then the cancel tag U+E007F. In the current Unicode versions the list has three entries: England (U+1F3F4 U+E0067 U+E0062 U+E0065 U+E006E U+E0067 U+E007F), Scotland (U+1F3F4 U+E0067 U+E0062 U+E0073 U+E0063 U+E0074 U+E007F), and Wales (U+1F3F4 U+E0067 U+E0062 U+E0077 U+E006C U+E0073 U+E007F). The table of D3 is authoritative, not this list.
- **Permitted_Tag_Sequence**: An occurrence of an RGI_Tag_Sequence as a contiguous code point sequence in the text, with the base U+1F3F4 directly before the first Tag_Character and no other code point between any two of its code points. The Tag_Characters of a Permitted_Tag_Sequence are not Hidden_Code_Points.
- **Hidden_Code_Point**: A Tag_Character, Zero_Width_Character, or Bidi_Control_Character, except a Permitted_ZWJ and except a Tag_Character that belongs to a Permitted_Tag_Sequence.
- **HTML_Comment_Opener**: The four-code-point sequence U+003C U+0021 U+002D U+002D. This document spells it by code point so that the scanner does not flag this file.
- **HTML_Comment_Closer**: The three-code-point sequence U+002D U+002D U+003E.
- **HTML_Comment**: A span that starts at an HTML_Comment_Opener and ends after the next HTML_Comment_Closer, or at the end of the text when no closer follows.
- **Emoji_Code_Point**: A code point with the Unicode property `Extended_Pictographic`, using the Unicode version recorded in the design document.
- **Emoji_Modifier**: U+FE0F (variation selector 16) or a code point in U+1F3FB to U+1F3FF (skin tone modifiers).
- **Permitted_ZWJ**: A U+200D whose nearest preceding code point that is not an Emoji_Modifier is an Emoji_Code_Point, and whose nearest following code point that is not an Emoji_Modifier is an Emoji_Code_Point. This is the standard emoji ZWJ sequence, such as a family emoji.
- **Ordinary_Text**: Text that contains no Hidden_Code_Point (a Permitted_ZWJ is not one) and no HTML_Comment_Opener. Hangul, emoji, combining marks, Latin letters, digits, punctuation, and line breaks are ordinary.
- **Finding**: One result of the Blacklight_Scanner (Requirement 3).
- **Rendering**: The visible, escaped, ASCII-only spelling of the hidden content of a Finding (Requirement 3).
- **Provenance_Record**: One text the agent read during a session, with its source identifier, kind, and content (Requirement 8).
- **Provenance_Log**: An ordered list of Provenance_Records. The list order is the reading order.
- **Needle**: One address, host, or file path taken from an `Effect` or `ObservedEvent` of a `GhostReport` (Requirement 9).
- **Thread_Link**: The result of looking up one Needle (Requirement 10): either the cause line or an explicit `not-found`.
- **Cause_Line**: The line of a Provenance_Record where a Needle first appears.
- **Revealed_Text**: The text of a Provenance_Record in which each maximal run of Tag_Characters that is covered by a Finding of category `tag` is replaced by its Rendering decoded form (Requirement 3, criterion 4); the Tag_Characters of a Permitted_Tag_Sequence stay unchanged. The Red_Thread_Tracer searches the Revealed_Text so that a destination hidden in Tag_Characters is still found.
- **Line_Break**: U+000A, U+000D U+000A (counted as one), or a lone U+000D.
- **Reference_Machine**: An Apple M1 machine, as in the `ghost-runner` spec.
- **Short_Run**: The property-based test run on file save: at least 100 generated examples per property, finishing within 60 s.
- **Nightly_Run**: The property-based test run with at least 10,000 generated examples per property and no time limit.

## Requirements

### Requirement 1: Placement, Purity, and Portability

**User Story:** As a template user, I want the possession detector to be a dependency-free pure function, so that the Playground, the hook, and my own agent app run the same detection without a server.

#### Acceptance Criteria

1. THE Blacklight_Scanner, Sanitizer, and Red_Thread_Tracer SHALL be implemented in TypeScript with zero runtime dependencies; the package that contains them SHALL list no entry under `dependencies`.
2. THE Blacklight_Scanner, Sanitizer, and Red_Thread_Tracer SHALL perform no file I/O, no network call, no process execution, no `eval` or dynamic code execution, and no LLM call, and SHALL read no clock, random source, or environment variable.
3. THE detection logic SHALL use only ECMAScript built-ins and SHALL reference no Node-only global (`process`, `Buffer`, `require`, `node:*` modules) and no DOM-only global (`window`, `document`, `TextEncoder`, `URL`).
4. THE package that contains the detection logic SHALL type-check with no DOM type library and no Node type library loaded.
5. THE detection logic SHALL pass its test suite under Node and once under a browser-like environment; the choice of that environment is a design decision (Design Decision D2).
6. THE package that contains the detection logic SHALL respect the dependency direction of the structure steering: `core/` depends on no other folder of this repository, and `apps/*` and `integrations/*` may depend on `core/` and `ui/`; the package placement is a design decision (Design Decision D1).
7. THE Scan_Entry_Point SHALL keep any file reading in a thin adapter module separate from the detection logic, so that criteria 2 and 3 hold for the detection logic.
8. THE detection logic SHALL export `scanText`, `sanitizeText`, `collectNeedles`, `traceRedThread`, `serializeProvenanceLog`, and `parseProvenanceLog` through the public entry point of its package.

### Requirement 2: Hidden Character Detection (Blacklight, P7 Positive Direction)

**User Story:** As a security reviewer, I want every hidden Unicode character in a text to be found, so that an instruction that a human cannot see cannot reach the agent unnoticed.

#### Acceptance Criteria

1. WHEN `scanText(text)` is called with text that contains a Tag_Character (U+E0000 to U+E007F) that does not belong to a Permitted_Tag_Sequence, THE Blacklight_Scanner SHALL return at least one Finding of category `tag` that covers that code point.
2. WHEN `scanText(text)` is called with text that contains a Zero_Width_Character other than a Permitted_ZWJ (U+200B, U+200C, U+200D, U+2060, or U+FEFF), THE Blacklight_Scanner SHALL return at least one Finding of category `zero-width` that covers that code point.
3. WHEN `scanText(text)` is called with text that contains a Bidi_Control_Character (U+202A to U+202E or U+2066 to U+2069), THE Blacklight_Scanner SHALL return at least one Finding of category `bidi` that covers that code point.
4. THE Blacklight_Scanner SHALL flag a Hidden_Code_Point at every position of the text, including the first code point, the last code point, a position directly after a Line_Break, and a position inside a word.
5. THE Blacklight_Scanner SHALL flag U+FEFF at the first code point of the text in the same way as at any other position.
6. WHEN `scanText(text)` is called with a text that contains no Hidden_Code_Point and no HTML_Comment, THE Blacklight_Scanner SHALL return a result with an empty `findings` array.
7. IF `scanText(text)` is called with a string that contains an unpaired surrogate code unit, THEN THE Blacklight_Scanner SHALL treat that code unit as one ordinary code point and SHALL NOT throw.
8. THE Blacklight_Scanner SHALL treat an empty string as Ordinary_Text and return an empty `findings` array.
9. WHEN `scanText(text)` is called with text that contains a Permitted_Tag_Sequence, THE Blacklight_Scanner SHALL return no Finding that covers any code point of that Permitted_Tag_Sequence (the base U+1F3F4 and its Tag_Characters including the cancel tag U+E007F).
10. THE Blacklight_Scanner SHALL recognize a Permitted_Tag_Sequence only by exact match of the whole code point sequence against the RGI_Tag_Sequence table of Design Decision D3, so that a Tag_Character is allowed only as part of a complete listed sequence.
11. THE Blacklight_Scanner SHALL return a `tag` Finding that covers every Tag_Character of each of these cases: a Tag_Character that is not part of any Permitted_Tag_Sequence; a Tag_Character with no base U+1F3F4 directly before its run; a run after U+1F3F4 that is a prefix of a listed sequence but lacks the cancel tag U+E007F; a run after U+1F3F4 that has the form of a flag (tag letters then U+E007F) but is not listed, such as the tag letters `gbxyz`; and a run after U+1F3F4 that begins like a listed sequence but has other Tag_Characters before its first U+E007F.
12. WHEN Tag_Characters follow a Permitted_Tag_Sequence directly, THE Blacklight_Scanner SHALL keep the Permitted_Tag_Sequence unflagged (the base U+1F3F4, its Tag_Characters, and its cancel tag U+E007F) and SHALL return a `tag` Finding that covers every appended Tag_Character, starting at the code point directly after the cancel tag U+E007F of the Permitted_Tag_Sequence and ending after the last Tag_Character of the run.

### Requirement 3: Finding Position and Rendering

**User Story:** As a reviewer, I want each finding to say where it is and what it hides, so that I can read the hidden instruction without a special tool.

#### Acceptance Criteria

1. THE Blacklight_Scanner SHALL return one Finding per maximal run of consecutive Hidden_Code_Points of the same Hidden_Category, and one Finding per HTML_Comment.
2. THE Finding SHALL carry these fields: `category` (a Hidden_Category), `line` (1-based), `column` (1-based, counted in code points from the start of the line), `offset` (0-based, counted in code points from the start of the text), `length` (number of code points covered), `codePoints` (the covered code points as numbers, in text order), `firstCodePoint` (the first code point written as `U+` followed by at least four uppercase hexadecimal digits), and `rendering` (a string).
3. THE Blacklight_Scanner SHALL count lines by Line_Break, so that the first code point of the text has `line` 1 and `column` 1, and the code point after a Line_Break has `column` 1 on the next line.
4. WHERE a Finding has category `tag`, THE Blacklight_Scanner SHALL set `rendering` to the ASCII string obtained by decoding each Tag_Character in the range U+E0020 to U+E007E to the code point obtained by subtracting 0xE0000 from it, and SHALL spell every other Tag_Character as `<U+XXXX>` with at least four uppercase hexadecimal digits.
5. WHERE a Finding has category `zero-width` or `bidi`, THE Blacklight_Scanner SHALL set `rendering` to the concatenation, in text order, of `<U+XXXX NAME>` for each covered code point, using these names: U+200B `ZERO WIDTH SPACE`, U+200C `ZERO WIDTH NON-JOINER`, U+200D `ZERO WIDTH JOINER`, U+2060 `WORD JOINER`, U+FEFF `ZERO WIDTH NO-BREAK SPACE`, U+202A `LEFT-TO-RIGHT EMBEDDING`, U+202B `RIGHT-TO-LEFT EMBEDDING`, U+202C `POP DIRECTIONAL FORMATTING`, U+202D `LEFT-TO-RIGHT OVERRIDE`, U+202E `RIGHT-TO-LEFT OVERRIDE`, U+2066 `LEFT-TO-RIGHT ISOLATE`, U+2067 `RIGHT-TO-LEFT ISOLATE`, U+2068 `FIRST STRONG ISOLATE`, U+2069 `POP DIRECTIONAL ISOLATE`.
6. THE `rendering` of every Finding SHALL consist only of printable ASCII code points (U+0020 to U+007E), so that printing a Finding never reproduces a hidden character.
7. WHERE a decoded Tag_Character rendering contains a printable ASCII code point, THE Blacklight_Scanner SHALL keep that code point unchanged in `rendering`, so that `rendering` of a run that encodes the ASCII text `abc` equals `abc`.
8. THE Blacklight_Scanner SHALL return `findings` sorted by `offset` ascending, and for equal `offset` by Hidden_Category in the order `tag`, `zero-width`, `bidi`, `html-comment`.
9. WHERE a Hidden_Code_Point lies inside an HTML_Comment, THE Blacklight_Scanner SHALL return a Finding for the HTML_Comment and a separate Finding for the Hidden_Code_Point run, so that the two Findings may overlap.
10. FOR ALL texts, THE `line`, `column`, and `offset` of every Finding SHALL identify the same code point: the code point at `offset` in the text, counted in code points, SHALL be the code point at `line` and `column` (position round-trip).
11. WHERE a `tag` Finding follows a Permitted_Tag_Sequence directly, THE Blacklight_Scanner SHALL start that Finding at the first appended Tag_Character, SHALL cover only the appended Tag_Characters, and SHALL set `rendering` from those code points only, so that a Permitted_Tag_Sequence followed by the Tag_Characters that encode `abc` yields one Finding whose `offset` is the position directly after the cancel tag U+E007F and whose `rendering` is `abc`.

### Requirement 4: Emoji ZWJ Allowance and False-Positive Immunity (P7 Negative Direction)

**User Story:** As a user who writes Korean text and emoji, I want ordinary text to be left alone, so that the blacklight does not cry wolf and I do not turn it off.

#### Acceptance Criteria

1. WHEN `scanText(text)` is called with a Permitted_ZWJ (U+200D between two Emoji_Code_Points, with any Emoji_Modifiers directly next to those emoji skipped), THE Blacklight_Scanner SHALL NOT return a Finding for that U+200D.
2. IF a U+200D has a non-emoji code point or the start or end of the text as its nearest preceding or following code point that is not an Emoji_Modifier, THEN THE Blacklight_Scanner SHALL return a `zero-width` Finding that covers that U+200D.
3. IF a U+200D is directly next to another Hidden_Code_Point, THEN THE Blacklight_Scanner SHALL return a `zero-width` Finding that covers that U+200D, because a Hidden_Code_Point is not an Emoji_Code_Point.
4. WHEN `scanText(text)` is called with Ordinary_Text that consists only of Hangul syllables (U+AC00 to U+D7A3), Hangul Jamo (U+1100 to U+11FF), emoji (including ZWJ sequences, U+FE0F, skin tone modifiers, and the England, Scotland, and Wales flag emoji as Permitted_Tag_Sequences), combining marks (U+0300 to U+036F), printable ASCII, and Line_Breaks, THE Blacklight_Scanner SHALL return an empty `findings` array.
5. THE Blacklight_Scanner SHALL NOT flag U+034F (combining grapheme joiner), U+FE0F, U+FE00 to U+FE0E, U+00AD, or U+200E and U+200F, because they are outside the Hidden_Category definitions of this spec.
6. THE design document SHALL record the Unicode version of the `Extended_Pictographic` table and of the RGI_Tag_Sequence table used by the Blacklight_Scanner, and the method that generated both (Design Decision D3).
7. THE Blacklight_Scanner SHALL use one Unicode/Emoji version and one generation method for the `Extended_Pictographic` table and the RGI_Tag_Sequence table.

### Requirement 5: HTML Comment Detection in Markdown

**User Story:** As a security reviewer, I want comments that markdown renderers hide to be found, so that an instruction placed in a comment cannot hide in a README or a steering file.

#### Acceptance Criteria

1. THE `scanText` function SHALL accept an optional `markdown` option of type boolean, and WHERE the option is absent, THE Blacklight_Scanner SHALL behave as if `markdown` is `true`.
2. WHERE `markdown` is `true` and the text contains an HTML_Comment_Opener, THE Blacklight_Scanner SHALL return a Finding of category `html-comment` that starts at that HTML_Comment_Opener.
3. THE Finding of an HTML_Comment SHALL have `length` equal to the number of code points from the HTML_Comment_Opener to the end of the HTML_Comment, including the opener and the closer.
4. WHERE an HTML_Comment_Opener has no later HTML_Comment_Closer, THE Blacklight_Scanner SHALL end the HTML_Comment at the end of the text.
5. THE Blacklight_Scanner SHALL return one Finding per HTML_Comment, scanning for the next HTML_Comment_Opener after the end of the previous HTML_Comment, so that nested openers inside one comment do not produce extra Findings.
6. WHERE a Finding has category `html-comment`, THE Blacklight_Scanner SHALL set `rendering` to the comment content between the opener and the closer (or the end of the text), with every code point outside U+0020 to U+007E replaced by `<U+XXXX>` (at least four uppercase hexadecimal digits) and every Line_Break replaced by the two-character text `\n`.
7. WHERE `markdown` is `false`, THE Blacklight_Scanner SHALL return no Finding of category `html-comment`.
8. THE Blacklight_Scanner SHALL flag an HTML_Comment wherever it appears, including inside a fenced code block, because the scanner does not parse markdown structure (Open Item O2).

### Requirement 6: Determinism and Robustness of the Scan

**User Story:** As a hook author, I want the scan to give the same answer every time and to finish quickly, so that it fits the 60-second hook limit and can be tested as a property.

#### Acceptance Criteria

1. FOR ALL texts and options, THE Blacklight_Scanner SHALL return structurally equal results when called twice with the same arguments (determinism).
2. THE Blacklight_Scanner SHALL NOT modify its arguments and SHALL NOT hold state between calls.
3. THE Blacklight_Scanner SHALL return a result that is JSON-serializable, such that `JSON.parse(JSON.stringify(result))` is recursively structurally equal to `result`.
4. THE Blacklight_Scanner SHALL run in time linear in the number of code points of the text.
5. WHEN `scanText(text)` is called with a text of 1 MiB of ordinary ASCII characters, THE Blacklight_Scanner SHALL return within 1 second on the Reference_Machine.
6. THE Blacklight_Scanner SHALL NOT throw for any string argument, including strings of any length that the JavaScript engine can hold.

### Requirement 7: Sanitize

**User Story:** As a user who found a possessed file, I want one operation that strips the hidden text and keeps the rest, so that I can purify the file without retyping it.

#### Acceptance Criteria

1. WHEN `sanitizeText(text, options)` is called, THE Sanitizer SHALL return a string obtained by removing from `text` every code point that lies inside a Finding returned by `scanText(text, options)`, using the same `markdown` option.
2. THE Sanitizer SHALL repeat the scan and removal until `scanText` returns no Finding, because removing a code point can join the remaining code points into a new HTML_Comment_Opener.
3. WHEN `scanText(text, options)` returns no Finding, THE Sanitizer SHALL return a string equal to `text`.
4. THE Sanitizer SHALL return a string `s` for which `scanText(s, options).findings` is empty (clean result).
5. FOR ALL texts, `sanitizeText(sanitizeText(text, options), options)` SHALL equal `sanitizeText(text, options)` (idempotence).
6. WHERE `markdown` is `false`, THE Sanitizer SHALL return a string that equals `text` with every Hidden_Code_Point removed and every other code point kept in its original order (visible-character preservation).
7. WHERE `markdown` is `true`, THE Sanitizer SHALL return a string that is a subsequence of the code points of `text` and SHALL keep every code point of `text` that lies outside every HTML_Comment and is not a Hidden_Code_Point, unless the repetition of criterion 2 removed it.
8. THE Sanitizer SHALL keep every Permitted_ZWJ and the whole emoji ZWJ sequence around it intact.
9. THE Sanitizer SHALL keep Hangul, emoji, combining marks, and Line_Breaks of `text` unchanged when they are not part of a Finding.
10. THE Sanitizer SHALL be a pure function that does not modify its arguments and that returns equal results for equal arguments.
11. THE Sanitizer SHALL keep every Permitted_Tag_Sequence intact (the base U+1F3F4, its Tag_Characters, and its cancel tag U+E007F) and SHALL remove only the other Tag_Characters, so that a Permitted_Tag_Sequence followed by appended Tag_Characters becomes exactly the Permitted_Tag_Sequence, and the idempotence of criterion 5 holds for texts that contain a Permitted_Tag_Sequence.

### Requirement 8: Provenance Record Format (Red Thread Input)

**User Story:** As the future `ghost-log` hook author, I want a fixed record format for what the agent read, so that I can store it during a session and the red thread can use it later.

#### Acceptance Criteria

1. THE Provenance_Record SHALL carry these fields: `source` (a non-empty string that identifies the origin, such as a file path or a URL), `kind` (one of `file`, `issue`, `web`, `other`), and `content` (a string with the full text that the agent read).
2. THE Provenance_Record SHALL be JSON-serializable and SHALL contain no function, `undefined`, `Date`, `Map`, `Set`, or circular reference.
3. THE Provenance_Log SHALL be an array of Provenance_Records in reading order, so that an earlier index means the agent read the text earlier.
4. THE possession module SHALL export `serializeProvenanceLog(log)`, which returns a JSON string, and `parseProvenanceLog(text)`, which returns the Provenance_Log or a list of validation errors.
5. WHEN `parseProvenanceLog(text)` is called with a string that is not valid JSON, THE possession module SHALL return an error whose message states that the JSON is invalid, and SHALL NOT throw.
6. IF a parsed record has an empty `source`, a `kind` outside the four allowed values, a `content` that is not a string, or an unknown extra field, THEN `parseProvenanceLog` SHALL return an error that names the zero-based record index and the field, and SHALL NOT return a partial log.
7. THE `parseProvenanceLog` function SHALL accept the empty array `[]` and return an empty Provenance_Log.
8. FOR ALL valid Provenance_Logs, `parseProvenanceLog(serializeProvenanceLog(log))` SHALL return a log that is recursively structurally equal to `log` (round-trip property).
9. THE record format SHALL define no field that holds a clock value, a session identifier, or a secret value; the hook that fills the log is out of scope.

### Requirement 9: Needle Extraction

**User Story:** As the red-thread feature, I want the addresses and paths of a ghost run collected in one list, so that each can be traced to its cause.

#### Acceptance Criteria

1. WHEN `collectNeedles(report)` is called with a `GhostReport` (or an object with the fields `effectsOutside` and `observedEvents` of that type), THE Red_Thread_Tracer SHALL return one Needle for each `Effect.destination` in `effectsOutside`, one Needle for each `ObservedEvent.destination` that is defined, and one Needle for each `ObservedEvent.path` that is defined.
2. THE Needle SHALL carry these fields: `value` (the string), `origin` (one of `effect`, `observed-destination`, `observed-path`), and `stepIndex` (the index in `effectsOutside` for an `effect`, and the `stepIndex` of the `ObservedEvent` for the other origins).
3. THE `collectNeedles` function SHALL return Needles ordered first by `stepIndex` ascending, then by `origin` in the order `effect`, `observed-destination`, `observed-path`, then by the original array order.
4. IF a `destination` or `path` value is an empty string, THEN THE Red_Thread_Tracer SHALL skip it and SHALL NOT return a Needle for it.
5. THE `collectNeedles` function SHALL NOT remove duplicate values, so that every occurrence in the report keeps its own Needle.
6. THE `collectNeedles` function SHALL NOT modify the report and SHALL return equal results for equal reports.

### Requirement 10: Red Thread Lookup

**User Story:** As a reviewer of a blocked action, I want a line from the text the agent read that explains where the address came from, so that I can see which document possessed the agent.

#### Acceptance Criteria

1. WHEN `traceRedThread(log, needles)` is called, THE Red_Thread_Tracer SHALL return one Thread_Link per Needle, in the same order as `needles`.
2. WHEN a Needle `value` occurs as a substring of the Revealed_Text of at least one Provenance_Record, THE Red_Thread_Tracer SHALL return a Thread_Link with `status` equal to `found` and with the `source`, `kind`, `recordIndex`, `line`, `column`, `lineText`, and `hidden` fields of the first occurrence.
3. THE Red_Thread_Tracer SHALL define the first occurrence as the occurrence with the lowest `recordIndex`, then the lowest `line`, then the lowest `column`.
4. THE `line` of a Thread_Link SHALL be 1-based and counted by Line_Break within the `content` of the record, and `column` SHALL be 1-based and counted in code points, using the coordinates of the original `content`.
5. THE `lineText` of a Thread_Link SHALL be the line of the original `content` that holds the occurrence, with every Hidden_Code_Point and every other code point outside U+0020 to U+007E replaced by `<U+XXXX>` (at least four uppercase hexadecimal digits) and truncated to at most 200 code points.
6. WHERE the occurrence lies inside a run of Tag_Characters that the Revealed_Text decoded (a run covered by a `tag` Finding, including Tag_Characters appended after a Permitted_Tag_Sequence), THE Red_Thread_Tracer SHALL set `hidden` to `true` and SHALL report `column` of the first Tag_Character of that decoded run; otherwise THE Red_Thread_Tracer SHALL set `hidden` to `false`.
7. IF the full Needle `value` has no occurrence and the `value` has the form `<scheme>://<host>[:<port>][/<rest>]` with a non-empty `<host>`, THEN THE Red_Thread_Tracer SHALL search for `<host>` as a second key and SHALL set `matchedKey` to `host`; otherwise `matchedKey` SHALL be `value`.
8. WHEN the Red_Thread_Tracer searches for a host key, THE Red_Thread_Tracer SHALL compare ASCII letters case-insensitively and SHALL accept an occurrence only when the code point before it is not one of `A-Z`, `a-z`, `0-9`, `_`, `.`, `-` and the code point after it is not one of `A-Z`, `a-z`, `0-9`, `_`, `-`.
9. WHEN the Red_Thread_Tracer searches for a `value` as a path or full-value key, THE Red_Thread_Tracer SHALL compare code points exactly (case-sensitive).
10. IF a Needle has no occurrence for any of its keys in any Provenance_Record, THEN THE Red_Thread_Tracer SHALL return a Thread_Link with `status` equal to `not-found` and no `source`, `line`, or `column`, and SHALL NOT throw and SHALL NOT guess a cause.
11. IF the Provenance_Log is empty, THEN THE Red_Thread_Tracer SHALL return a `not-found` Thread_Link for every Needle.
12. THE `traceRedThread` function SHALL be a pure function: it SHALL NOT modify its arguments, and it SHALL return structurally equal results for structurally equal arguments.
13. THE Thread_Link SHALL be JSON-serializable.
14. THE Red_Thread_Tracer SHALL run in time linear in the total number of code points of all `content` strings multiplied by the number of Needles.

### Requirement 11: Scan Entry Point for the blacklight-steering Hook

**User Story:** As the author of the `blacklight-steering` hook, I want one callable interface that scans a saved file and tells me whether to warn, so that I can build the hook without reimplementing detection.

#### Acceptance Criteria

1. THE Scan_Entry_Point SHALL export a function `scanFiles(paths, options)` that returns a Promise of a `BlacklightReport`, and a pure function `scanTexts(inputs, options)` that does the same for in-memory `{ path, text }` inputs.
2. THE `BlacklightReport` SHALL carry these fields: `outcome` (one of `clean`, `findings`, `error`), `files` (one entry per input path, in input order, each with `path`, `findings`, and an optional `error` string), and `totalFindings` (the sum of the Finding counts).
3. WHEN every input scans without a Finding and without an error, THE Scan_Entry_Point SHALL set `outcome` to `clean`.
4. WHEN at least one input has a Finding and no input has an error, THE Scan_Entry_Point SHALL set `outcome` to `findings`.
5. IF at least one input file cannot be read, THEN THE Scan_Entry_Point SHALL set `outcome` to `error`, SHALL set the `error` string of that entry to a message that names the path and the failure reason, and SHALL still scan and report every other readable input.
6. THE Scan_Entry_Point SHALL define the interface-level exit semantics `clean` = 0, `findings` = 1, `error` = 2, exported as a pure function `exitCodeFor(outcome)`; the mapping of these codes to hook behavior is decided in the `kiro-integration` spec.
7. WHERE the path of an input ends in `.md`, `.markdown`, or `.mdx` (compared case-insensitively), THE Scan_Entry_Point SHALL scan with `markdown` set to `true`; for every other path, THE Scan_Entry_Point SHALL scan with `markdown` set to `false`.
8. THE file reading adapter SHALL read each file as UTF-8, SHALL replace an invalid byte sequence with U+FFFD, and SHALL NOT write to, rename, or delete any file.
9. THE Scan_Entry_Point SHALL export a pure function `formatReport(report)` that returns a plain-text report with one line per Finding in the form `<path>:<line>:<column> <category> <firstCodePoint> <rendering>` and a final summary line with the outcome and `totalFindings`.
10. THE `formatReport` function SHALL write the `rendering` of a Finding quoted and truncated to at most 200 code points, and SHALL append the text `[truncated]` after the closing quote when it truncated, so that a hidden instruction decoded from a file does not enter the agent's context as an unquoted, unbounded text.
11. THE `formatReport` output SHALL contain only printable ASCII code points and Line_Breaks, and SHALL NOT contain a literal hidden character.
12. WHEN `scanTexts` is called twice with equal arguments, THE Scan_Entry_Point SHALL return structurally equal reports (determinism).
13. THE Scan_Entry_Point SHALL call no LLM API and SHALL finish scanning one file of 1 MiB within 1 second on the Reference_Machine, so that the hook limit of 60 seconds is not at risk.
14. THE `Scan_Entry_Point` SHALL NOT install, register, or configure any hook; the `blacklight-steering` hook is created by the `kiro-integration` spec.

### Requirement 12: Claim Boundaries

**User Story:** As a judge or a reader of the README, I want the claims of the possession detector to match what it does, so that I can trust the claims that remain.

#### Acceptance Criteria

1. THE P7 claim SHALL read: text that contains a Hidden_Code_Point of the categories `tag`, `zero-width`, or `bidi` is always flagged, and Ordinary_Text is never flagged (Ordinary_Text includes the England, Scotland, and Wales flag emoji, whose Tag_Characters are allowed only as an RGI_Tag_Sequence); this claim applies everywhere, because the Blacklight_Scanner is a pure function.
2. THE HTML_Comment detection SHALL be documented as an additional category that applies only where `markdown` is `true`, and not as a part of the P7 negative direction.
3. THE documentation of this spec (README section and tool descriptions that cite it) SHALL state that text analysis does not catch every injection.
4. THE documentation SHALL state that the action-based criterion (a secret file read followed by an unapproved network attempt produces `block`) is owned by the `wards` spec as P6, and the possession detector SHALL NOT assert P6.
5. THE documentation SHALL state that invisible characters outside the categories of this spec (for example U+115F, U+3164, and look-alike letters from other scripts) are not detected.
6. THE documentation SHALL state that the red thread is a lookup for a literal occurrence, and that an address that the agent built from several pieces, encoded, compressed, or encrypted does not produce a `found` Thread_Link.
7. THE red thread SHALL NOT be used as a verdict input; a `not-found` Thread_Link SHALL NOT change a `pass`, `warn`, or `block` verdict.

### Requirement 13: Property-Based Tests

**User Story:** As a maintainer, I want the safety property P7 and the lookup rules checked on random input, so that false positives and missed characters are found by the machine and not by a judge.

#### Acceptance Criteria

1. THE test suite SHALL use `vitest` and `fast-check`, and SHALL run every property below with at least 100 generated examples in a Short_Run and at least 10,000 generated examples in a Nightly_Run.
2. FOR ALL Ordinary_Text strings generated from Hangul syllables, Hangul Jamo, emoji (including generated ZWJ sequences with U+FE0F and skin tone modifiers, and the three flag emoji England, Scotland, and Wales, each as the full RGI_Tag_Sequence), combining marks, printable ASCII, and Line_Breaks, `scanText(text).findings` SHALL be empty (P7, negative direction).
3. FOR ALL Ordinary_Text strings that contain no emoji, and FOR ALL positions in the text, and FOR ALL code points chosen from the Hidden_Code_Points (including U+200D and every Tag_Character), inserting that code point at that position SHALL produce a text whose `scanText` result contains a Finding whose `offset`, `line`, and `column` identify the inserted code point (P7, positive direction).
4. FOR ALL Ordinary_Text strings with a run of ASCII text `t` (printable ASCII only) encoded as Tag_Characters (each code point of `t` plus 0xE0000) inserted at any position, THE Finding of category `tag` at that position SHALL have `rendering` equal to `t`.
5. FOR ALL texts, `sanitizeText` SHALL satisfy idempotence (Requirement 7, criterion 5), the clean result (criterion 4), the unchanged result for text without findings (criterion 3), and visible-character preservation for `markdown` set to `false` (criterion 6).
6. FOR ALL texts and options, `scanText` and `sanitizeText` SHALL be deterministic and SHALL NOT modify their input (Requirement 6 criteria 1 and 2, Requirement 7 criterion 10).
7. FOR ALL generated Findings, THE position round-trip of Requirement 3 criterion 10 SHALL hold.
8. FOR ALL generated Provenance_Logs and generated Needles, THE `traceRedThread` result for a `found` Thread_Link SHALL point to the first occurrence: no earlier record, no earlier line within the same record, and no earlier column within the same line contains the matched key under the rules of Requirement 10.
9. FOR ALL generated Provenance_Logs in which a Needle `value` is placed in a chosen record at a chosen line, `traceRedThread` SHALL return a `found` Thread_Link whose `recordIndex` is not greater than the chosen record index.
10. FOR ALL generated Provenance_Logs and Needles that contain no occurrence of the Needle `value` or its host key, THE `traceRedThread` result SHALL be `not-found`.
11. FOR ALL valid Provenance_Logs, THE round-trip of Requirement 8 criterion 8 SHALL hold.
12. THE test suite SHALL include example-based tests for: a family emoji (allowed), a U+200D between two Latin letters (flagged), a leading U+FEFF (flagged), a README text with a destination hidden in Tag_Characters that the red thread finds with `hidden` equal to `true`, an HTML_Comment without a closer, and an HTML_Comment_Opener created by the removal of a U+200B (sanitize repeats).
13. THE test suite SHALL include an example test that runs the P7 negative property with the text of the five Ghost Shell scenarios of `docs/plan.md` and the Korean text of the plan headings, and expects no Finding.
14. FOR ALL Ordinary_Text strings, FOR ALL positions in the text, and FOR ALL generated non-empty sequences of Tag_Characters, inserting a Permitted_Tag_Sequence followed directly by that sequence at that position SHALL produce a text whose `scanText` result contains `tag` Findings that cover every appended Tag_Character and no Finding that covers any code point of the Permitted_Tag_Sequence (P7, positive direction for a Tag_Character appended after a flag).
15. FOR ALL generated runs of Tag_Characters that are not a Permitted_Tag_Sequence when placed at their position (a run with no base U+1F3F4 directly before it, a prefix of a listed sequence without the cancel tag U+E007F, a flag-shaped run that is not listed, or a run that begins like a listed sequence and continues with other Tag_Characters before the first U+E007F), `scanText` SHALL return `tag` Findings that cover every Tag_Character of the run.
16. FOR ALL generated texts that contain Permitted_Tag_Sequences with or without appended Tag_Characters, `sanitizeText` SHALL keep every Permitted_Tag_Sequence intact, SHALL remove every appended Tag_Character, and SHALL be idempotent (Requirement 7 criteria 5 and 11).
17. THE test suite SHALL include example tests for: each of the three flag emoji alone (no Finding); a flag followed by the Tag_Characters that encode a short ASCII word (a Finding that covers only the appended Tag_Characters and has that word as `rendering`); the U+1F3F4 and the tag letters `gbeng` without the cancel tag (flagged); a flag-shaped run that is not listed (flagged); and Tag_Characters with no base (flagged).

### Requirement 14: Repository Hygiene for Hidden Characters

**User Story:** As a maintainer, I want the possession tests and docs to avoid hidden characters in committed files, so that the repository passes its own blacklight.

#### Acceptance Criteria

1. THE test code SHALL construct every Hidden_Code_Point with a Unicode escape sequence or with `String.fromCodePoint`, and SHALL NOT contain a literal Hidden_Code_Point.
2. THE spec documents, fixtures, README sections, and source files of this feature SHALL contain no literal Hidden_Code_Point.
3. THE spec documents and fixtures of this feature SHALL contain no literal HTML_Comment_Opener; where a document must name it, it SHALL name it by code point.
4. THE repository SHALL contain a test that runs `scanText` through the Scan_Entry_Point over the files of `.kiro/specs/possession/` and `.kiro/steering/`, and the test SHALL expect the outcome `clean`.
5. THE Scan_Entry_Point test fixtures that need hidden input SHALL build the text in memory and SHALL NOT write a file that contains a literal Hidden_Code_Point to the repository.
6. THE fixtures that name hosts SHALL use only reserved domains (`.example`, `.test`, `.localhost`, `.invalid`), and the fixtures that name secrets SHALL use only canary values such as `sk-CANARY-abc123`.

## Out of Scope

- The `blacklight-steering` hook, the `ghost-log` hook, and any other hook: they are created by the `kiro-integration` spec. This spec defines only the entry point and the record format that they call.
- Filling the Provenance_Log during a session (the Post Tool Use hook `ghost-log`), and storing it in a file or in a graveyard.
- The MCP tool wiring for `blacklight` (and `ghost_trace`) in `integrations/mcp/`.
- The UI rendering of the blacklight toggle, the glowing hidden characters, the red thread line, and the purify button (`ui` and the apps).
- The action-based possession criterion (secret read then unapproved network attempt), which is P6 of the `wards` spec, and the content inspection of payloads.
- Detection of compression, encryption, and DNS-exfiltration (one character at a time) of secrets.
- Detection of look-alike (homoglyph) letters, of invisible characters outside the four categories, and of natural-language prompt injection in visible text.
- Allowing Tag_Character sequences other than the RGI_Tag_Sequence list (for example custom or future subdivision flags that the D3 table does not list); the scanner flags them.
- Markdown structure parsing (fenced code blocks, inline code, nested lists).
- Kiro Crew integration.

## Design Decisions and Open Items

The following decisions are left to the design phase and are recorded here so that they are not lost.

- **D1, package placement.** The structure steering says `core/` holds the possession detector. The design phase decides between a module inside `core/` and a separate package. Either way, the detection logic keeps zero runtime dependencies, and `core/` depends on no other folder. The file reading adapter of Requirement 11 criterion 7 lives in a package that is allowed to use Node (not in the pure detection module).
- **D2, browser-like test environment.** The design phase chooses how the test suite runs once under a browser-like environment, without adding a runtime dependency.
- **D3, emoji tables.** The design phase chooses the Unicode/Emoji version and the generated tables for `Extended_Pictographic` and for the RGI_Tag_Sequence list (`RGI_Emoji_Tag_Sequence` in `emoji-sequences.txt`), uses the same version and the same generation method for both, and decides how the tables are regenerated. A new Unicode version that adds a tag sequence changes the allowed set only through that regeneration.
- **O1, leading U+FEFF.** A byte-order mark at the start of a file is flagged (Requirement 2 criterion 5), as the plan lists U+FEFF. If real files in `.kiro/**` produce noise, the design phase may add an option that the Scan_Entry_Point sets; the default stays "flag".
- **O2, HTML comments in code fences.** A comment inside a fenced code block is visible to a human in the rendered page, but the scanner flags it, because it does not parse markdown. This is the conservative choice. The design phase may add structure-aware scanning only if the false-positive rate on `.kiro/**` files requires it.
- **O3, plan wording.** `docs/plan.md` says the scan covers "HTML comments in markdown" and that the red thread finds where an address "first appeared". This spec turns both into the precise rules above (Requirements 5 and 10). If the plan wants a different meaning for "first appeared" (for example the last text read before the action), this spec needs a change.
