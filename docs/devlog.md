### Implementation starts (Kiro CLI, from 09:20)

- Method: Claude Code calls Kiro's spec agent with `kiro-cli chat --v3 --no-interactive --agent spec --trust-workspace --trust-all-tools --output-format stream-json "<instructions>"`. Kiro starts its built-in sub-agent (`spec-task-execution`) for each task and records the state in tasks.md and `tasks.meta.json`. Implementation runs follow the waves of tasks.md.
- pnpm runs as `corepack pnpm` without a global install (Kiro put `packageManager: pnpm@12.21.0` in the root). pnpm 12 blocks build scripts, so `pnpm-workspace.yaml` got `allowBuilds: { esbuild: true }`. The Node version is 20.20.2, so vitest is pinned to 3.x and typescript to 5.9.

The `main` of core is the TypeScript source, so Node users (the hooks, ghost-runner) need a build.

### Experiment C: a primitive-shape arm and drawer with `@mujoco/mujoco` (outside the repository, throwaway code)

The single-thread build plus Web Workers needs no headers, so it also runs on GitHub Pages.
- Scene: an arm of capsules and boxes (4 hinges and 2 fingers), a drawer on a slide joint, and a vase on top of the cabinet. The plan is reach → grasp → pull → release, with IK by `mj_jacSite`.

### Experiment A: a ghost in a Docker box (outside the repository, throwaway code)

Conclusion: **plan A works and finishes well within the 60-second hook limit.** But the DNS wait and a time limit for offline commands must go into the design.

- Environment: Apple M1, macOS 26.6.2, Docker Desktop (Engine 29.8.2), image `node:20-alpine` plus sqlite, strace, and curl.
- Fake repository: 3,945 files (72 MB, no node_modules), a SQLite database with 1,206 rows of users, a fake canary `.env`, `"clean": "rm -rf data"`, 2 links pointing outside the repository, and a watched folder outside the repository.
- Isolation (P1): across all 354 runs, the fingerprints of the original and of the watched folder stayed the same. `rm -rf link/` through a link pointing outside, deletion of absolute host paths and `$HOME`, and `rm -rf /tmp/*` inside the box did not reach the host. The fingerprint differed once, and the cause was not the ghost but a `git gc --auto` on the host. The product's P1 check must also filter such host-side changes.
- Copy: one `clonefile(2)` call on a folder takes 36 ms, `cp -cR` (cloning file by file) 778 ms. Node has no folder-level API, so a small helper is needed.
- diff: an lstat walk (not following links) plus size and mtime, hashing only files whose ctime is later than the copy time, gives a median of 88 ms. An overwrite that restored the size and mtime was still caught by ctime. `diff -rq` follows symbolic links and is dangerous.
- Total (copy, run, and diff, median of 5): 0.26 to 0.42 s. A pool of single-use containers started in advance: 0.16 to 0.31 s. With 19,345 files (276 MB): 0.7 to 1.9 s.
- Material for judgment: `DROP TABLE users` loses 1,206 rows, `rm -rf ./data ./build` deletes 515 entries, and for `npm run clean` the diff (not the command shape) caught 64 deletions in `data/`. `npm test` changes nothing.
- Pitfall 1: without network, every DNS lookup stalls for about 5 s. Because of npm's update check, `npm test` took 5.2 s and the `.env` exfiltration attempt 10.2 s. A fake recording DNS at 127.0.0.1 inside the box (`--dns 127.0.0.1` works together with `--network none`) brought these down to 0.3 to 0.6 s.
- Pitfall 2: `npm install` never finishes offline and was killed at 58 s. The box needs a 20 to 30 s limit, and going over it must return warn.
- Network recording: the fake DNS recorder logged host names, canaries in HTTP bodies, the SNI of HTTPS, and connection attempts to 5432, but misses direct IP connections. strace catches direct IPs too and adds 0.1 to 0.8 s (no `SYS_PTRACE` needed). With both on, it stays under 2 s. Even plain commands such as `npm test` try to reach `registry.npmjs.org`, so it must be on the allow list to avoid warn.
- Recommendation: folder clonefile, a pool of single-use containers (the scenarios still ran with hardening options such as `--cap-drop ALL`, `--read-only`, and `--dns 127.0.0.1`), the fake DNS recorder plus strace when needed, a ctime-based diff, and a 20 to 30 s limit in the box itself. A single long-lived shared container is not used, because state carries over between runs and other copies are visible.

### The gate in a real Kiro: sleeping Docker, host checks, `ask`, and the power in another project

- **Why.** The owner asked for an honest score against the judging criteria. The weakest point was the story of the product guarding Kiro itself: the gate had never run in our own Kiro. The plan:
  - fix the gate
  - check it in both hosts
  - switch it on for our own work
  - count the approvals for at least three days

  A video script and the Devpost text come after that.

- **Sleeping Docker (root cause).**
  - In Kiro IDE the gate fell back to static analysis.
  - Docker Desktop's Resource Saver stops its VM after 5 idle minutes, and the first engine call then takes about 1.9 s. The gate's 2 s check timed out. `docker version` does not wake the VM; `docker info` does.
  - Kiro added one wake retry (10 s) and a `docker-warmup` hook (commit 0372934).
  - Runs: 27.9, 1.1 and 0.4 credits.

- **Host checks before switching the gate on.** Claude Code ran them in scratch clones, in Kiro CLI 3.5.0 and Kiro IDE 1.4.236:
  - CLI: non-interactive runs, and an interactive chat in a pseudo-terminal.

  - Claude Code answered every approval prompt.

  | Check | CLI | IDE |
  |---|---|---|
  | `ls` | allowed (safe list) | allowed (safe list), then the IDE's own approval |
